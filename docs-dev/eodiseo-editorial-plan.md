# 어디서? — ChatGPT만으로 서비스 만들기 (연재 기획)

> **상태:** 소재 선정 / 미발행  
> **대상:** AX Notes Public의 Project + Note  
> **서비스:** 어디서? — 모임 장소를 함께 추천하고 투표로 결정하는 웹 서비스  
> **개발 기록:** `msaltnet/eodiseo` (비공개 저장소)

## 방향

**코드를 직접 작성하지 않고 ChatGPT와 대화하고, GitHub PR을 검토·머지하며 실제 서비스를 개발한 경험**을 기록한다.

목표는 개발 과정의 단계별 설명이나 AI 생산성 홍보가 아니다. ChatGPT가 요구를 잘 구현했는데도 예상과 다른 결과가 나온 **구체적인 사건 하나**를 잡고, 그때 무엇을 다시 생각하고 결정했는지를 보여준다.

- 기술 튜토리얼·PR 나열·일정표·성공담은 쓰지 않는다.
- 실제로 흥미로운 일이 있을 때만 글을 낸다. 정해진 편수와 발행 주기는 없다.
- 실패와 재작업을 감추지 않되, AI가 잘못한 일과 사람이 잘못 판단한 일을 구분한다.
- 이미 알려진 교훈을 억지로 붙이지 않는다. 뻔하면 발행하지 않는다.

## 우선 소재 — 첫 글 하나만 진행

### 1. ChatGPT에게 기능을 계속 추가했더니 투표가 안 보인다

**상태:** 첫 글 후보 (우선 진행)

모임 장소를 **투표로 결정**하는 서비스인데, 기능을 계속 추가하면서 기본 정보와 설정, 장소 추가, 후보 비교가 한 화면에 길게 쌓였다. ChatGPT는 요청을 구현했지만 사용자가 가장 먼저 해야 할 투표가 묻혔다.

- **읽을거리:** 기능을 많이 구현하는 것과 쓰기 좋은 제품을 만드는 것은 다르다.
- **실제 변화:** 투표 중심 화면 구성, 부가 기능 접기, 장소 추천 다이얼로그 분리. 이후 다이얼로그의 카드 중첩·스크롤 문제 같은 재작업도 발생.
- **근거:** 어디서? UX 개편 논의 및 eodiseo PR #68 전후의 변경·피드백.
- **시각 자료:** 투표 화면 개편 전/후 비교, 실제로 주고받은 핵심 요청 일부.
- **주의:** 새 UX가 완성됐거나 더 좋아졌다는 주장은 실제 화면을 확인한 뒤에만 쓴다.

**글 흐름 제안:** “투표하러 왔는데 투표가 안 보인다” → 그동안 추가한 기능과 화면 → ChatGPT에 다시 던진 요청 → 변화와 남은 문제 → 내가 해야 했던 판단.

## 다음 소재 후보 — 아직 발행 계획 없음

### 2. 이촌동을 검색했는데 이촌동이 안 나온다

지역을 정하고 싶었는데 검색 결과에 랜드마크나 장소가 등장했다. API가 결과를 반환하는 것과 사용자의 목적에 맞는 검색은 다르다.

- **핵심:** ‘지역을 정한다’와 ‘장소를 찾는다’는 전혀 다른 작업.
- **근거:** 지역 검색 개선 PR #50, Enter 키 동작 수정 PR #51.
- **발행 기준:** 실패 화면과 수정 결과를 비교할 수 있을 때만 작성.

### 3. 서버는 정상이라는데 모임을 만들 수 없다

Health Check는 정상이었지만 실제 모임 생성은 실패했다. 원인은 코드가 기대하는 스키마와 실제 개발용 Supabase DB의 차이였다.

- **핵심:** CI와 Health Check의 녹색 표시가 사용자 여정 전체의 정상 동작을 보장하지 않는다.
- **근거:** 개발 DB 스키마 정리·감지 PR #64, #66 및 관련 테스트·배포 기록.
- **발행 기준:** 당시 확인한 로그·검증 결과로 원인과 영향 범위를 재구성할 수 있을 때만 작성.

두 후보는 순서도, 발행 여부도 확정하지 않는다. 더 흥미로운 사례가 나오면 교체한다.

## 글 한 편의 편집 원칙

1. **시작:** 독자의 호기심을 끄는 실제 상황이나 한 문장.
2. **문제:** 원했던 행동과 실제로 벌어진 일을 짧게 대비.
3. **대화와 수정:** ChatGPT에게 무엇을 요청했고 무엇이 달라졌는지. 실제 프롬프트는 확보한 원문만 인용하고, 재구성은 명시한다.
4. **결과:** 전/후 화면, 테스트 결과 또는 검증 가능한 PR 내용.
5. **Aftertaste:** 그 경험에서만 나올 수 있는 짧은 생각 한 문장.

기존 AX Notes의 개인적인 말투와 유머는 살리되 억지 감동·교훈은 빼고, 길이는 사건 하나를 설명하는 데 필요한 만큼만 쓴다.

## 저장소 반영·공개 기준

- **지금은 이 기획 문서만 추가한다.** Project 카드나 공개 Note는 아직 만들지 않는다.
- 첫 글 원고가 읽을 만해지면 `src/content/collections/`에 **어디서? Project**를 등록하고 `src/content/notes/`에 첫 Note를 추가한다. 기존 콘텐츠 스키마와 발행 흐름을 재사용한다.
- `eodiseo`는 비공개 저장소다. 공개 글에 비공개 PR 링크만 던져놓지 말고, 글에서 이해할 수 있도록 변경 요점과 허용 가능한 캡처를 제공한다.
- 배포 전 초대 링크, PIN, 관리자 비밀번호, API 키, 참가자 식별 정보, 개인 모임 데이터를 제거한다.
- 글 작성 → 내용·사실 확인 → 사이트 검증(`npm run verify`) → PR 리뷰 → 머지 순서로 진행한다.
